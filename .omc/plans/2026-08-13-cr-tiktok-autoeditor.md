## 1. Requirements Summary

**Цель:** кинуть N записей матчей CR в папку → одна команда → готовое TikTok-видео.

Зафиксировано в интервью:

| Параметр | Значение |

| Выход | 2 режима: `--montage` (одно видео 30-60с) и `--clips` (N отдельных клипов) |

## 2. Архитектурные решения (варианты + выбор)

### D1. Детект хайлайтов — как находить «моменты» без звука

| Вариант | За | Против | Вердикт |
|---|---|---|---|
| A. Обученная CV-модель / YOLO на события | точность | нужен датасет, разметка, вес, GPU | ❌ оверкилл |
| B. Только generic-motion (диффы кадров) | 20 строк | ловит любую суету, не отличает корону от спама юнитов | ⚠️ база, мало |
| C. Хардкод-координаты HUD Clash Royale | точно | ломается на другом телефоне/разрешении/патче | ❌ хрупко |
| **D. Авто-обучение ROI по частоте изменений + generic-motion** | без разметки, само подстраивается под разрешение, устойчиво к патчам | нужна валидация на реальном футаже | ✅ **выбран** |

**Механика D (ядро идеи):** счётчик корон в HUD меняется **редко** (0-6 раз за матч), таймер — **каждую секунду**, арена — **каждый кадр**. Строим карту частоты изменения пикселей по верхней полосе экрана и берём кластеры с частотой `1 ≤ f ≤ 8` → это и есть счётчики корон. Тайминги их изменений = события «башня упала». CR-агностично, не зависит от координат и разрешения.

### D2. Рендер — как собирать финал

| Вариант | За | Против | Вердикт |
|---|---|---|---|
| A. Посегментный рендер → concat демюксер | просто, параллелится | потеря поколения, куча temp-файлов, склейки на границах | ❌ |
| **B. Один проход `filter_complex` (trim/setpts/zoompan/concat + overlay + audio)** | нет потери качества, ноль temp, одна команда | длинный граф, отладка | ✅ **выбран** (граф дампится в `out/debug/filtergraph.txt`) |

### D3. Сабы/мемы — чем рисовать

| Вариант | За | Против | Вердикт |
|---|---|---|---|
| A. `drawtext`/ASS в ffmpeg | нативно | **фильтров нет в сборке** → нужен `brew reinstall ffmpeg` (риск апгрейда на 9.0) | ❌ |
| **B. Pillow → RGBA-слой → `overlay.mov` (qtrle) → `overlay` фильтр** | любая анимация, эмодзи, PNG-стикеры, ноль системных зависимостей | свой рендер текста | ✅ **выбран** |

### D4. Seam «анализ ↔ рендер»

`EditPlan` — JSON-контракт между детектом и рендером. `--analyze-only` пишет его, `--from-plan` рендерит из него. Даёт: ручную правку монтажа, детерминизм, кеш, быструю итерацию эффектов без пере-анализа.

## 4. Пайплайн

```
inbox/*.mp4
  │
  ├─ media.probe()      ffprobe → {w,h,fps,duration}
  ├─ media.sample()     ffmpeg -vf fps=10,scale=160:-2 → numpy (кеш в .crcut/)
  │
  ├─ detect.signals()   motion[t]  (маска: только арена, без HUD и руки карт)
  │                     flash[t]   (доля пикселей luma>240 — взрывы/спеллы)
  │                     scene[t]   (scdet — границы матчей внутри файла)
  │                     endscreen[t] (долгая статика + всплеск насыщенности = VICTORY/DEFEAT)
  │
  ├─ detect.learn_roi() карта частоты изменений верхней полосы (2 fps, нативный кроп)
  │                     кластеры 1≤f≤8 → ROI счётчиков корон
  │                     изменения ROI  → crown_events[timestamps]
  │
  ├─ plan.score()       окно = [t-4.5s, t+2.0s] вокруг события, merge пересечений
  │                     score = 3.0*crown + 1.0*norm(motion) + 0.8*norm(flash)
  │                             × 1.5 если событие в последних 30с (клатч/овертайм)
  │                     × 2.0 если это 3-я корона (победный хит)
  │
  ├─ plan.build()       montage: cold-open (1.4с пик + «СМОТРИ ДО КОНЦА») →
  │                              хронология топ-K окон до --duration → аутро 1.5с
  │                     clips:   каждое окно → отдельный файл 10-25с
  │                     beat-map: librosa.beat_track(музыка) → снап границ к битам (±250мс, трим лид-ина)
  │                     эффекты:  punch-zoom 1.0→1.12 (0.35с) на кадре короны
  │                               shake 0.25с, slowmo 0.5x на ±0.4с вокруг короны
  │                               speed 1.6x на скучном лид-ине
  │                     → out/plan.json
  │
  ├─ overlay.render()   Pillow: капс-сабы с pop-анимацией (0.6→1.15→1.0 за 180мс),
  │                     обводка + тень, счётчик «КОРОНЫ 2/3», тонкий прогресс-бар сверху,
  │                     мем-стикеры из assets/memes → out/debug/overlay.mov (qtrle, alpha)
  │
  └─ render.run()       ОДИН ffmpeg: N видео-входов + overlay.mov + музыка + SFX
                        trim/setpts/zoompan/crop/concat → overlay → format
                        libx264 crf 18 preset veryfast, aac 192k, +faststart
                        → out/montage_YYYYMMDD-HHMM.mp4  (+ .txt с названием и хештегами)
```

## 11. Журнал реализации (Стадии 0-4 — сделано 2026-08-13)

Файлы: `src/crcut/{cli,media,detect,plan,render}.py`, `tests/fixtures/make_fake_cr.py`,
`tests/test_{detect,plan,render}.py`. 26 тестов зелёные (3.8с).

**Отклонения от плана:**

| Что | Как в плане | Как сделано | Почему |
|---|---|---|---|
| Структура плана монтажа | `montage` / `clips` — разные ветки | единый `Group` (montage = 1 группа, clips = N групп) | один путь рендера вместо двух |
| Слоумо на короне | эффект внутри сегмента | отдельный сегмент со `speed=0.55` | рендеру не нужна переменная скорость внутри сегмента |
| Сине-красное разделение корон (твои / чужие) | — | **не делал** | без реального футажа это спекуляция; сейчас все события равны |
| Детект конца матча | отдельный `endscreen` детектор | `action_end` по спаду motion | дешевле, той же задачи хватает |

**Два бага, пойманных фикстурой:**

1. **Детектор ловил таймер.** `cv2.dilate` растил компоненту на края блока таймера, а подсчёт
   событий шёл по **bbox**, а не по маске «редких» пикселей → изменения таймера утекали внутрь.
   Плюс `max_events=8` совпало с числом слитых событий таймера на 24-секундной фикстуре.
   Фикс: счёт только по `rare`-маске + `max_events=6` + отбраковка **периодичных** ROI
   (коэффициент вариации интервалов < 0.15 = часы/анимация, не счёт).
2. **Бесконечный цикл в `_trim_to_target`.** При `out_duration`, севшем на `min_segment`,
   `room` становился ~1e-17 > 0, вычитание не меняло float → цикл не сходился (весь прогон вис).
   Фикс: epsilon `1e-3` вместо `0`. Регресс-тест: `test_trimming_converges_on_an_extreme_target`.

**Проверено на фикстуре:** 3/3 события короны найдены точно, таймер и арена не попали
(`out/debug/roi_fake_cr.png` — боксы ровно на счётчиках); рендер даёт 1080x1920 h264
yuv420p 30fps; `--clips` и `--from-plan` работают.

### 11.1. Решение D1 отменено реальным футажом (2026-08-13)

Первый прогон на трёх настоящих записях (384x832, 86-104с) показал, что предпосылка
D1 неверна: **Clash Royale не рисует счётчик корон во время матча**. В верхней части
кадра — рука противника, ник и таймер; короны видны только на финальном экране.
ROI-обучение находило 1-2 «события» на матч, и это были переходы на экран конца матча.

Проверенные замены (кадры и замеры — `out/probe/`):

| Гипотеза | Результат | Вердикт |
|---|---|---|
| Тряска камеры (`cv2.phaseCorrelate`) | медиана 0.07, пики в матче 3-6 (~50×) | ✅ сильный сигнал удара |
| Перманентный скачок яркости (исчезновение HP-плашки башни) | доминируют руки карт, башни не выделяются | ❌ |
| Стабильность HUD как гейт «матч идёт» | в матче 6-15, интро/финалка 39-54 | ✅ разделение без пересечений |

**Что стало вместо D1:** `motion + flash + shake` в робастных z-оценках → `hype`;
пики `hype` = хайлайты. Гейт матча — по стабильности HUD-строк относительно медианы
середины ролика, берётся самый длинный непрерывный «живой» отрезок. Детект склеек не
нужен. Удалены `learn_crown_rois`, `Roi`, `_change_masks`, `_is_periodic`,
`sample_strip`, `_motion_peaks`, `crown_word`/`CROWN_TITLES` и ROI-превью в `--debug`.

Гейт на реальных файлах: `3.1-97.2` / `7.9-85.5` / `5.3-81.4с` — совпадает с покадровой
проверкой. Третий баг: слияние соседних окон давало `lead` в 11.7с одним куском →
добавлен `PlanConfig.max_lead = 3.5`.

**Проверено на реальном футаже:** монтаж 42.0с из всех трёх матчей, 1080x1920 h264
yuv420p 30fps; 5 выборочных кадров — живой геймплей, экранов загрузки/победы нет.

**Следствия для критериев приёмки:** A1/A2 (recall событий короны) больше не применимы —
детектировать нечего. Заменяются на: гейт матча попадает в ±1с от ручной разметки, и
все хайлайты лежат внутри гейта.

### 11.2. Стадия 4 сделана (2026-08-13)

Сделано: `overlay.py` (сабы через Pillow), плавные переходы, панч-зум с тряской,
шкала досмотра, мем-стикеры, SFX. Тесты: 22 зелёных.

Что разошлось с планом п.16-17 и почему:

| План | Реально | Причина |
|---|---|---|
| Один сплошной RGBA-оверлей (`qtrle` .mov) | По одному тугому PNG на сабе, вход `-loop 1` | 42с × 30fps × 1080×1920 RGBA ≈ 10.5 ГБ через пайп |
| `drawbox` для прогресс-бара | `color` + `overlay` с `x='-W+W*t/T'` | в `drawbox` `t` — это толщина рамки, а не время; выражение `w='iw*t/T'` давало полную ширину с первого кадра |
| `crop` для панч-зума | `zoompan` | `crop` считает размер выхода один раз при конфигурации — зумить во времени им нельзя |
| Счётчик корон в оверлее | нет | корон в кадре нет (см. 11.1) |
| Слоумо «на короне» | слоумо на `hit` (0.55×) | то же самое |

Переходы: `xfade` 0.3с только там, где реально меняется кадр (`src` другой или
разрыв по времени > 0.05с). Внутри окна `lead → hit → tail` кадры непрерывны, фейд
там читается как заикание — жёсткий стык. На реальном футаже 6 переходов на 42.5с.

Грабли `xfade`: он отказывается работать, если у входов разные timebase. `zoompan`
ставит свой (`1/fps`), `concat` возвращает timebase входа — поэтому `settb=AVTB`
идёт **последним** в цепочке каждого сегмента и после каждого `concat`/`xfade`.

Проверено на реальном футаже (замеры, не «на глаз»): шкала досмотра 2.4/49.4/96.5%
ширины на 1/21/41с (ожидалось 2.4/49.4/96.4); панч-зум — левый шов пилларбокса
58 → 82 → 95px за 1.5с (95 = без зума), т.е. 1.10 → 1.0 как задумано.

## 11.3 Варианты и музыка (2026-08-13)

Запрос: «чтобы на выходе уже был готовый ролик или два-три варианта, можно туда
музыку подставлять трендовую».

**Варианты.** `--variants N` (по умолчанию 3). Один анализ → N групп в том же
`plan.json`, разные по трём осям сразу, иначе выбирать не из чего:

| | v1 | v2 | v3 |
|---|---|---|---|
| длина (`VARIANT_SCALE`) | ×1.0 | ×0.62 | ×1.28 |
| холодный старт | 1-й хайлайт по рейтингу | 2-й | 3-й |
| заголовок | сид `#0` | `#1` | `#2` |
| палитра переходов | сдвиг 0 | 1 | 2 |

Имена файлов — `montage_v{n}_<штамп>.mp4`, штамп один на прогон, чтобы варианты
одного прогона лежали рядом.

**Музыка.** Трендовые звуки лицензированы, скачивать их нечем и незачем: буст за
трендовый звук начисляется, только если звук прицеплен внутри TikTok. Поэтому:
треки из `assets/music/` крутятся по вариантам (`Group.music` перекрывает
`EditPlan.music`), а если папка пуста — синтезируется бед (`src/crcut/music.py`):
140 BPM, квадратные волны, кик и клэп, `np.tanh` вместо клиппинга. BPM известен
точно → сетка битов точная, `librosa` не нужна.

Проверено на реальном футаже: 3 файла 42.4 / 27.4 / 54.0с, 1080×1920 h264 + aac
48 кГц стерео, mean −21.9 дБ / max −5.6 дБ (не тишина), все склейки (18 / 12 / 23)
в пределах 1 мс от доли, шкала досмотра 2 / 47 / 97% на 0.5 / 13 / 26.5с. 23 теста
зелёные.

### 11.4 Сабы, озвучка и SFX (2026-08-13)

**Сабы.** Пул расширен с 6 до 30 фраз на язык и упорядочен парами «интрига →
расплата», чтобы любой непрерывный кусок читался как нагнетание. Курсор по пулу
сквозной на прогон (`_assign_captions(start=...)`, `_captions_used`), а не свой у
каждого варианта: три ролика одного прогона съедают ~20 фраз и ни одна не
повторяется (`test_no_caption_is_reused_across_variants`). Проверено на футаже:
18 подписей на 3 варианта, дублей нет.

**Озвучка.** Каждый саб зачитывается вслух. Дед делается, а не берётся: в macOS
ровно один русский голос (`Milena`, женский), поэтому синтез `say` проходит через
цепочку `AGE` (`src/crcut/voice.py`) — `asetrate=44100*0.78` + `atempo=1.2821`
(−4.3 полутона при неизменной длине, измерено 213 → 167 Гц), полоса 80–5000 Гц,
`vibrato=f=4.8:d=0.12`. Голос выбирается с учётом локали (`pick`) и задаётся по
началу имени (`resolve`), потому что macOS показывает `Grandpa (Англійська (США))`
и держит своего `Grandpa` на каждый язык. Реплики кэшируются по хэшу «текст +
голос + цепочка». Под голосом музыка приседает 0.9 → 0.55.

**SFX.** Та же политика, что и с музыкой: ничего не качается, всё синтезируется
(`src/crcut/sfx.py`, numpy → wav). Удар — суб-бум с падающей частотой плюс щелчок
шума, на каждый `hit`/`hook`. Файлы из `assets/sfx/` заменяют удар. (Свуш на
склейках был здесь же и удалён в 11.6 — звучал неприятно.)

Проверено на реальном футаже: 13 / 9 / 17 звуковых кью и 7 / 5 / 9 реплик на
вариант, 21 уникальный `vo_*.wav` на прогон, mean −21.0 дБ / max −1.9 дБ (без
клиппинга, `alimiter` держит). 26 тестов зелёные.

### 11.5 Голос: стили и реплики (2026-08-13)

**Проблема.** Дед из 11.4 звучал плохо, и виноват был сам сдвиг: −4.3 полутона на
`asetrate`+`atempo` мылит форманты, а полоса 80–5000 Гц дожимала остальное.

**Решение — сдвиг меньше, характер вокруг него.** `AGE` (одна строка) заменён на
`STYLES: dict[str, Style]`, где `Style = (rate, chain)`. Дефолтный `grandpa`: −3
полутона (0.84), `equalizer=f=220:g=+3` (тело), `equalizer=f=520:g=-3` (убрать
«коробку»), `deesser=i=0.4`, `vibrato=f=4.2:d=0.08`, `aecho=0.85:0.6:24:0.16`,
`acompressor` + `alimiter`. Ещё три стиля: `grandpa_deep` (−4 полутона, старый
вариант, но с новой обвязкой), `hype` (+0.85 полутона, 195 wpm, яркий), `clean`
(без сдвига вообще). Флаг `--voice-style`, ездит в `plan.json`.

Измеренная F0 (автокорреляция, реальный синтез `Milena`): сырой 219.4 Гц →
`grandpa` 183.8 → `grandpa_deep` 170.9 → `hype` 230.9 → `clean` 219.4.

**Реплики.** `Segment.adlib` — текст, который **только произносится** и никогда не
рисуется. Пул `ADLIBS`, 16 фраз на язык, вешается на каждый второй `tail`
(`_assign_adlibs`), курсор сквозной на прогон, как у сабов. В рендере реплика
ставится на `start + 0.25`, чтобы не наезжать на саб того же момента.

Проверено на футаже: 7/5/9 сабов + 3/2/4 реплики = 10/7/13 озвученных строк на
вариант, дублей реплик нет, mean −21.0/−19.8/−20.1 дБ, max −1.8/−1.8/−1.9 дБ.
27 тестов зелёные. Сэмплы для выбора стиля: `out/voice-demo/*.wav`.

### 11.7. Реальная музыка, меньше озвучки, хриплый стиль

**20 треков в `assets/music/`.** Скачаны с ccMixter через их публичный API
(`/api/query?f=json&lic=open&tags=…`), `lic=open` = CC-BY: коммерция и ремикс при
указании автора. Фильтр — инструментал, 60–330 с, BPM 118–160, максимум два трека на
автора. Отдаёт файл только с `Referer` со своей же страницы (`curl -e <page>`), иначе
403. Pixabay и Openverse отпали: Cloudflare и 401/429 соответственно. Атрибуция —
`assets/music/ATTRIBUTION.md` (файл / трек / автор / длина / BPM / лицензия / ссылка).

**Свой трек и своя сетка на вариант.** Раньше `build_plan(music=..., beats=...)` брал
один трек и одну сетку на весь прогон — с реальными треками (130–147 BPM, разные
фазы) два варианта из трёх снапились бы на чужую сетку. Теперь
`build_plan(tracks=[...], grids=[...])`, ротация по группам внутри плана,
`_snapped(segments, grid_of(i), cfg)`. Пост-обработка `group.music` в CLI удалена.
Какие три из двадцати — хэш имён исходников: другой `inbox/` → другая музыка, тот же
`inbox/` → повтор. Тест `test_each_variant_snaps_to_the_grid_of_its_own_track`
(120 BPM против 150 BPM).

**Меньше озвучки.** `Segment.narrate`: заголовок читается всегда, дальше через один;
реплики — через каждый третий хвост вместо каждого второго. 10/7/13 озвученных строк
→ 6/4/7. Реплики переписаны с точек на «!» и «…» — `say` по ним строит другую
интонацию, а на экран они всё равно не идут, так что пунктуация бесплатная.

**Дрожание.** `_recipe(style, text)` двигает скорость (±12 слов/мин) и высоту (±2.4%)
хэшем текста фразы. Детерминированно — кэш `vo_*.wav` продолжает попадать, но соседние
строки звучат по-разному; ровный питч на каждой строке и был главным признаком синтеза.

**`rasp`.** Пятый стиль по запросу «версия голосом Глада Валакаса». Голос конкретного
человека не клонируется — модели нет и делать этого не будем; `rasp` — типаж
треш-стрима: `acrusher` (грязь) + `aexciter` (гармоники), +6 дБ на 1.4 кГц и −4 дБ на
400 Гц (гнусавость), компрессор 8:1 и полоса 150–6000 Гц (крик в дешёвый микрофон).
Измерено: F0 185 Гц, пик 0.67, RMS 0.082 — против 172 Гц / 0.45 / 0.091 у `grandpa`.

Проверено: три разных трека на три варианта, 49 из 53 склеек в пределах 1 мс от доли
**своего** трека (остальные не двинулись из-за `beat_snap` / `min_segment`),
6/5/8 озвученных строк, демо `out/rasp-demo/`. 28 тестов зелёные.

### 11.8. Качество: настоящие песни, чистое сведение, 4:4:4 до конца

**Жалоба.** «Музыкальный фон либо слишком быстрый либо рыхлый» и «убери звуковые
эффекты на переключении кадров».

**SFX убраны совсем.** `src/crcut/sfx.py` удалён вместе с синтезом удара. Причина не
в тайминге, а в конструкции: моменты и есть места склейки, поэтому синтезированный
удар неизбежно попадал на каждую смену кадра. Осталось только то, что лежит в
`assets/sfx/`; пустая папка = звукового слоя нет.

**Музыка выбрана по метрикам, а не наугад.** Старый пул был проверен объективно
(`librosa`): три реально звучавших трека оказались наименее плотными в пуле
(`steady` 0.08 / 0.41 / 0.10 при медиане 0.25), а один — глухим (`centroid` 907 Гц).
То есть «рыхлый» — не вкусовщина, а измеримое свойство отбора. Отбор переделан:

1. 285 песен с ccMixter, теперь **с вокалом** (жанровые теги hiphop/rap/pop/funk/
   rock/house/…, 90–360 с, максимум 3 на автора) — «инструментал» из старого фильтра
   и давал лупы и стемы вместо песен;
2. первый проход по всем 305 (285 + старые 20): темп, `spectral_flatness`,
   `spectral_centroid`, крест-фактор, `steady` (10-й/90-й перцентиль RMS) и **чёткость
   доли** — автокорреляция огибающей атак на периоде такта (по ней и режем);
3. первый проход выигрывали спокойные вещи, поэтому второй по топ-90: энергия
   50–160 Гц, частота атак и RMS мастера;
4. 15 лучших с разбросом (≤1 на автора, ≤3 на жанр), каждый проверен `librosa.load` —
   один mp3 ffmpeg читал, а libsndfile нет, и он бы уронил прогон в `detect_beats`.

Итог: 89–136 BPM (было 129–144), `steady` 0.39–0.68, `centroid` 1287–2170 Гц.

**Окно снапа стало зависеть от темпа.** `beat_snap` был фиксированный 0.30 с. На
89 BPM доля идёт через 0.674 с, то есть склейка может стоять в 0.337 с от ближайшей —
дальше окна, и такая склейка просто оставалась мимо. На синтезированных бедах (140 BPM,
0.43 с между долями) это не проявлялось никогда. Теперь окно `max(cfg.beat_snap,
период / 2)`, период берётся медианой разностей самой сетки. На 89-BPM варианте худшая
склейка была в 307 мс от доли, стала в 2 мс; по всем трём вариантам максимум 3 мс.
Тест `test_a_slow_track_still_gets_every_cut_on_a_beat`.

**Сведение.** Всё к 48 кГц / stereo / fltp на входе (`sidechaincompress` не берёт
разные форматы). Музыка приседает через `sidechaincompress` по шине голоса, а не
фиксированным `volume=0.55` на весь ролик — между репликами она на полном уровне.
Шина голоса — `asplit=2[vox][key]`: метку в filtergraph можно потребить один раз, а
неподключённый выход `asplit` — жёсткая ошибка, поэтому сплит только когда музыка
есть. Дальше `amix=duration=longest:normalize=0` → `alimiter` → `loudnorm=I=-14:
TP=-1.5:LRA=11` → `aresample=48000:filter_size=64` (`loudnorm` отдаёт 192 кГц; `soxr`
не собран в этом ffmpeg — проверено, `Requested resampling engine is unavailable`).
AAC 256 kbps.

**Картинка.** `-sws_flags lanczos+accurate_rnd+full_chroma_int` (swscale работает и
внутри `zoompan`, который пересчитывает каждый кадр панча), `format=yuv444p` на всю
цепочку с единственной конверсией в `yuv420p` на `[vout]` (сабы и стикеры кладутся
поверх, в половинной цветности у цветного текста расползаются края), `-crf 16 -preset
medium` (TikTok пережмёт — мастер должен пережить второе поколение), явные
`bt709` для colorspace/primaries/trc.

Проверено на трёх вариантах с `rasp`: интегральная громкость −13.1 / −13.4 / −13.3 LUFS
(разброс 0.3 LU — раньше варианты приходили с разной громкостью), пик −1.2 / −5.4 /
−1.7 dBFS вместо прижатого к лимитеру −0.0 dB, склейки в 2 / 3 / 1 мс от доли своего
трека. 29 тестов зелёные.

### 11.9. Клипы: ≤20с, папка на матч (2026-08-13)

Запрос: «нарезки до 20 секунд с комментариями и музыкой, разделять в папки по
видосу, без двух вариантов». Ответ на открытый вопрос из §12: клип = одно событие,
не сжатый матч.

**Раскладка.** `out/clips/<стем матча>/<стем>_NN.mp4` + `.txt` рядом (заголовок и
хэштеги). Имя самодостаточно после заливки; клипы внутри матча хронологические,
не по скору — папка заливается пачкой и должна читаться по порядку матча.

**Окна.** `_merge_windows` (правильный для монтажа) на реальном футаже схлопнул
18 хайлайтов в 6 клипов: окна ±8/4с зацепляются цепочкой, и от МАТС2 остался один
клип с последним пиком. Для клипов — `_split_windows(min_gap=5.0)`: пики ближе 5с —
один момент (двойной снос башен), мержатся; дальше — сплит по середине между пиками.

**Длина.** `clip_max=20.0` — обещание, не ориентир: снап к битам сначала,
жёсткий трим потом (`_trim_to_target(..., slack=0.0)`); укорачивается последний
шот, где ничего не режется в долю — музыка просто затухает. Лид в клипе — все 8с
окна (клип рассказывает весь пуш), в монтаже лид по-прежнему капится.

**Музыка.** Трек на клип, ротация по пулу из 15: 18 подряд залитых клипов не
звучат как одна песня.

Проверено на трёх матчах: 18 клипов (6+6+6), 6.8–12.4с, все ≤20с; папки
`out/clips/{МАТС2,МАТЧ1,МАТЧ3}/`; спот-чек МАТЧ3_01: −13.5 LUFS, пик −1.6 dBFS.
32 теста зелёные (4 новых: группа на хайлайт, кап на медленной сетке,
несхлопывание цепочки, раскладка по матчам).

**Дополнение (тот же день): клип = 2–3 события.** «можно в клипе несколько
событий 2-3 делать» — одиночные клипы по ~10с читались куце. `_chunked()` бьёт
окна матча на сбалансированные хронологические чанки до `clip_events=3`
(5 окон → 3+2, не 3+1+1: хвостовой одиночка читается как обрезок).
`segments_for()` получил `budget = clip_max / len(chunk)`: хит целый (это
пейофф), остаток 70% в лид (на 1.25×) / 30% в хвост — завязка должна читаться,
послевкусие лишь висит. Чанк из одного события даёт байт-в-байт старое
поведение: бюджет 20с упирается в границы окна раньше кап. Треков в ротацию —
по числу чанков (`ceil(хайлайтов/3)` на матч), не хайлайтов.

Адверсариальное ревью диффа (8 агентов, каждая находка перепроверена репро-кодом)
подтвердило три дефекта, все починены:
1. Бюджет забивал клип ровно в 20с без запаса → после снапа трим срезал с конца
   и мог съесть хит последнего события (на разреженной сетке — весь хайлайт,
   оставив висячий лид). Фикс: `budget = (clip_max − 2·beat_snap) / k`.
2. `_trim_to_target` резал вслепую с конца. Фикс: `spare_hits=True` для клипов —
   сначала бреются хвосты (с конца) и лиды (с начала, событие остаётся слитным
   со своим хитом), хиты — только если больше нечего.
3. `_snapped` без ограничителя соседей: растянутый хвост события N залезал в лид
   N+1 того же матча → видимая перемотка назад внутри клипа (0.53% клипов на
   реальных темпах, до 2.2с на медленных). Фикс: клэмп на границе событий,
   только когда сосед реально был по ту сторону до растяжки (хук монтажа —
   не стена). Заодно закрыт тот же латентный баг в монтаже.
35 тестов (2 новых регрессионных: разреженная сетка не стоит хайлайту хита;
снап не перематывает клип назад).
